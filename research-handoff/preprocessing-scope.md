# 前処理の方針

## 目的

前処理は、条件抽出やEMICの代替ではありません。
前処理の役割は、`before` / `after`と観測用workloadから、後段が実行・観測できる入力を作ることです。
研究の中心はJavaScript片を小さくすることではなく、`before` / `after`の組から適用条件を抽出することです。
構造の整理と実行単位の準備は、条件抽出を可能にするための前提として扱います。
入力空間を有限分割し、代表値を実行して条件仮説を検証する方針は、`ai-research-workspace/my-research/current.md`の「EMIC (入力限定等価確認器): 4 オラクル」に対応します。

現在の主な要件は次の二つです。

1. EMICで実行可能であること。
2. pruningの試行回数を抑えるため、不要なコンテキストを圧縮すること。

## 実行可能性の定義

「Nodeプロセスが終了する」だけを実行可能とはみなしません。

最低限、次を区別します。

- `parseable`: 入力を構文解析できる。
- `setup_resolved`: 依存関係や初期化を解決できる。
- `target_reached`: before / afterの対象コードに到達した。
- `workload_executed`: 観測対象のworkloadが実行された。
- `observable`: EMICが比較対象の結果を観測できる。
- `inconclusive`: 実行不能または観測不能で、等価性を判断できない。

両側が同じ依存関係エラーになるケースを、等価性の証拠として扱ってはいけません。
`equal`、`not_equal`、`inconclusive`は、前処理段階の実行状態と分けて記録します。

## 圧縮の基本方針

最初から全ケースに動的な削減を繰り返すのではなく、静的な構造整理を基本にします。

候補となる流れは次のとおりです。

1. `before` / `after`の変更領域をAST上で特定する。
2. 対象領域から参照される自由変数、宣言、制御依存、import / requireを求める。
3. 対象コードを呼び出す最小のentrypointとworkloadを残す。
4. 計測ループ、ログ、時間測定、結果報告など、意味論の観測に不要な処理を除く。
5. before / afterの両方を実行し、対象到達と観測可能性を確認する。
6. まだ大きいケースにだけ、予算制限付きのAST削減を適用する。

ここでの圧縮は、条件を推測する処理ではありません。
どの入力値で等価になるかという意味論的分類は、後段の条件抽出に残します。

## 実行環境の扱い

### CommonJSを初期プロファイルにする理由

次プロジェクトでは、CommonJSを最初に実装する実行プロファイルとして扱います。
これはJavaScript全体をCommonJSとみなすという意味ではありません。
EMICの実行条件と依存解決を固定し、適用条件抽出の研究に集中するための初期スコープです。

GitHub上のJavaScriptを収集できなくなるわけではなく、収集したコードのうち、現在のexecutorで再現可能な範囲だけを主評価・実行対象にします。
パターン外81issueの拡張性評価でも、実行プロファイルの対応範囲がカバレッジ上限を決めるため、プロファイル非対応のケースは`unsupported`として内訳ごと報告します。

### browser / jsdomを独立した実行契約にする

Selakovicのケースに必要な場合は、CommonJSとは別のbrowser / jsdomプロファイルを追加します。
browser / jsdomをCommonJSのfallbackとして扱わず、独立した実行契約として定義します。

### 初期スコープ外の形式

ESM、TypeScript、JSX、bundler依存、複雑なmonorepo構成は、初期プロファイルの対象外です。
これらをCommonJSへ機械的に変換して救済することも、初期要件には含めません。

前処理がすべての形式を一つの方式で救済することは目標にしません。
入力ごとに実行プロファイルを判定し、対応できないものは明示的に`unsupported`または`inconclusive`とします。
旧形式への互換性のためのfallbackを、新契約の初期要件には含めません。

論文では「現代のJavaScript全体を解析する」と主張せず、制御された実行プロファイル上で適用条件を抽出する手法として位置づけます。
ESM、TypeScript、JSX、bundler依存などの未対応ケースは、失敗として隠さず、適用範囲の境界として件数と除外理由を明示します。
将来、Selakovic外のOSSで外部確認を行う場合も、対応プロファイルに入るケースだけを実行対象とし、非対応ケースを同じ境界として記録します。

## 評価する指標

前処理は、実行成功率だけでは評価しません。

なお、2026-07の二本柱化（[corpus/README.md](../corpus/README.md)）により、前処理の段階別通過率はパターン外81issueの拡張性評価の指標に直結します。
以下の指標は、開発時の前処理品質の指標と、拡張性の報告値の両方に使われます。

- 対象到達率
- 観測可能率
- `inconclusive`率
- ASTノード数またはトークン数の削減率
- pruningに渡す候補数
- pruningの総試行回数
- 1ケースあたりの実行時間

圧縮率が高くても対象到達率が低い入力は、良い前処理結果とはみなしません。

## 採用を決めていない方式

方式に関する未決定事項は、[blocking-decisions.md](blocking-decisions.md)に集約します。
これらは関連研究の候補であり、現行実装の方式を引き継ぐ決定ではありません。
